## 5. Sprint C 验收:BLAKE3 重复文件检测(核心,~15 分钟)

> M6 主线核心交付。需先准备一个能产生重复文件的目录。

### 5.1 准备测试样本(选其一)

**方案 A**:用 `/Downloads` 或 `/Pictures` 等真实场景(推荐)。

**方案 B**:手动构造一组重复文件(更可控):

```bash
mkdir -p /tmp/diskmind-dedup-test
cd /tmp/diskmind-dedup-test
# 8 MB 随机文件,复制 3 份(同内容 / 不同名)
dd if=/dev/urandom of=base.bin bs=1M count=8 2>/dev/null
cp base.bin copy1.bin
cp base.bin copy2.bin
# 另一组,5 MB 副本 ×2
dd if=/dev/urandom of=other.bin bs=1M count=5 2>/dev/null
cp other.bin other-copy.bin
# 噪声文件(独一无二,不会进任何组)
dd if=/dev/urandom of=unique.bin bs=1M count=3 2>/dev/null
ls -lh
```

预期:5 个 8 MB + 5 MB + 5 MB + 8 MB + 8 MB + 3 MB = 6 个文件,**期望产生 2 个重复组**(8 MB × 3 / 5 MB × 2),浪费 = 8×2 + 5×1 = **21 MB**。

## 8. 已知遗留 / 永久取消

### 8.1 推迟到 Round 34

- **scan_result 加 `hash_head` / `hash_full` 缓存列 + dup_group 关系**:首版 BLAKE3 6 GB/s 够快(2000 候选 ~ 秒级),真要做缓存等用户实际抱怨"反复扫慢"。设计文档 §3.3 已留入口。
- **dedup 端到端测试**(硬链接 / 跨卷 / 截断 / power-loss):单测已覆盖核心算法(11 个),端到端需要管理员权限 + 多卷挂载 + 模拟掉电,CI 不稳定,等集成测试环境一起做。
- **Sprint D · 关键 UI 组件单测补测**(CommandPalette / BreadcrumbBar / TrashTable / ScanProgressCard):本轮未上,但不影响发布,这些组件历史回归率低,后续 Round 34 一并做。

### 8.2 永久取消(经过推理,见待办 §3.3 详细)

- **跨设备同步(云盘配置 / cleaning history)**:违背"数据不出本机"的隐私承诺。用户需要时自行复制 `diskmind.sqlite`。
- **插件机制(WASM / .so 加载)**:Round 29 的 `rules.toml` 热更新已经覆盖了"社区扩展规则库"这个 90% 的场景,引入 plugin runtime 会带来沙箱逃逸风险,ROI 倒挂。
