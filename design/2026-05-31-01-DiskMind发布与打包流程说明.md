
## 1. release.yml 究竟做了什么

`.github/workflows/release.yml` 是一个**多平台并行**的发布流水线,核心目的是:**一次推 tag,自动产出 macOS aarch64 / macOS x86_64 / Windows x64 三套安装包,统一挂到 GitHub Release 草稿上**。

### 1.1 触发方式(二选一)

| 触发方式 | 用途 | 产物去向 | 是否创建 Release |
|---|---|---|---|
| **`push tag`**(`git push origin v*`) | **正式发版** | GitHub Releases 页(**草稿**,需手动 Publish)+ Artifact | ✅ 是 |
| **`workflow_dispatch`**(Actions UI 手动按钮) | 日常调试 / 内部分发 | 只产 Artifact(30 天保留) | ❌ 否 |

设计动机:
- 正式版本必须经过 tag 这一步审计动作,避免随手 push 误发版
- 调试场景用手动触发,不污染 Release 列表,30 天自动回收

### 1.2 平台矩阵

```yaml
matrix:
  - macos-latest + --target aarch64-apple-darwin  → DiskMind_*_aarch64.dmg
  - macos-latest + --target x86_64-apple-darwin   → DiskMind_*_x86_64.dmg
  - windows-latest                                 → DiskMind_*_x64-setup.exe + *.msi
```

三个 job 在 `fail-fast: false` 下**并行**跑,任一平台失败不会拖累其他平台。

### 1.3 关键步骤逐项解读

#### 步骤 1:Checkout + 安装工具链

```
Checkout source        → actions/checkout@v6
Install pnpm           → pnpm/action-setup@v6 (v10)
Setup Node.js          → actions/setup-node@v6 (Node 24)
Install Rust stable    → dtolnay/rust-toolchain@stable (按 matrix 装对应 target)
Rust cache             → swatinem/rust-cache@v2 (cache app/src-tauri/target/)
Install frontend deps  → pnpm install --frozen-lockfile (按 pnpm-lock.yaml 严格安装)
```

`--frozen-lockfile` 是关键:CI 端不会重新解析依赖版本,防止 lockfile 漂移导致 dev / CI 环境构建产物有差异。

#### 步骤 2:版本同步(仅 tag 触发)

```yaml
- name: Sync version across all manifest files (tag trigger only)
  if: github.event_name == 'push'
  working-directory: app
  run: |
    VERSION="${{ github.ref_name }}"     # v0.3.0
    pnpm sync-version "$VERSION"          # → 改写 tauri.conf.json + Cargo.toml
```

`scripts/sync-version.js` 做的事:
1. 把 `v0.3.0` → `0.3.0`(去 `v` 前缀)
2. 校验版本号格式 `^\d+\.\d+\.\d+`(否则 exit 1)
3. 改写 `app/src-tauri/tauri.conf.json` 的 `version` 字段
4. 改写 `app/src-tauri/Cargo.toml` 的 `version = "..."`

**为什么必须在 CI 里做,而不是手工改完再 push tag?**
- 避免本地版本号漂移:开发分支 `version: "0.1.0"`,只在打包瞬间临时被改成 tag 版本号,**改动不 commit**,下次开发分支继续保持开发版本号。
- tauri-action 在后续 `Build & publish` 步骤里读这两个文件决定**产物文件名**(如 `DiskMind_0.3.0_aarch64.dmg`),版本号同步是它出对正确文件名的前提。

**为什么手动触发要 skip?**
- `workflow_dispatch` 时 `github.ref_name` 是分支名(如 `main`),不符合 `^\d+\.\d+\.\d+`,`sync-version.js` 会直接 exit 1,整个 workflow 提前中断。
- 手动产物沿用 manifest 里现有版本号 + commit sha 区分(参见 `Upload artifacts` 步骤的 `name: diskmind-${matrix.label}-${github.sha}`),不需要版本号 sync。

#### 步骤 3:Smoke 测试三件套

```
Run frontend tests           → pnpm test          (vitest run,单测)
Run frontend typecheck       → pnpm exec vue-tsc --noEmit
Run backend tests            → cargo test --lib   (Rust 单测)
```

任一失败 → workflow 红 → tauri-action 不会跑 → 产物**不会**进 Release。这是质量底线门禁。

#### 步骤 4:打包 + 发布(分支处理)

**tag 触发分支**(`if: github.event_name == 'push'`):

```yaml
- uses: tauri-apps/tauri-action@v0
  with:
    projectPath: app
    tagName: ${{ github.ref_name }}        # v0.3.0
    releaseName: "DiskMind ${{ github.ref_name }}"
    releaseBody: |
      ## DiskMind 桌面磁盘分析与清理工具
      ... (固定模板,包含 Gatekeeper / SmartScreen / 不支持自动更新 说明)
    releaseDraft: true                       # 产物挂草稿,需要手动 Publish
    prerelease: false
    args: ${{ matrix.args }}                 # --target aarch64-apple-darwin 等
```

tauri-action 内部依次做:
1. `pnpm tauri build` 触发 `beforeBuildCommand`(`pnpm build` → vite 产 `app/dist/`)
2. 然后 `cargo build --release` 编译 Rust(产 `app/src-tauri/target/<TARGET>/release/`)
3. 调 cargo-tauri 走平台特定的 bundler:
   - macOS:`bundle/dmg/*.dmg` + `bundle/macos/*.app.tar.gz`
   - Windows:`bundle/msi/*.msi` + `bundle/nsis/*.exe`
4. 把产物 upload 到 `v0.3.0` 这条 Release 草稿(同 tag 已存在的 Release 会复用,不会新建)

**手动触发分支**(`if: github.event_name == 'workflow_dispatch'`):

```yaml
- uses: tauri-apps/tauri-action@v0
  with:
    projectPath: app
    args: ${{ matrix.args }}
  # 不传 tagName / releaseName / releaseBody → 只 build,不 publish

- uses: actions/upload-artifact@v4
  with:
    name: diskmind-${{ matrix.label }}-${{ github.sha }}
    path: |
      app/src-tauri/target/*/release/bundle/dmg/*.dmg
      app/src-tauri/target/*/release/bundle/macos/*.app.tar.gz
      app/src-tauri/target/*/release/bundle/msi/*.msi
      app/src-tauri/target/*/release/bundle/nsis/*.exe
    retention-days: 30
```

产物落到对应 run 的 **Summary 页** → Artifacts 区域,30 天后自动回收。

## 2. 完整发布流程(以发版 `v0.3.0` 为例)

### 2.1 准备阶段:本地验证

```bash
# 站在仓库根
cd /Users/TerrellShe/Documents/personal/tt-projects/DiskMind

# 跑一遍跟 CI 一样的 smoke 门禁,提前发现问题
cd app
pnpm install --frozen-lockfile
pnpm test
pnpm exec vue-tsc --noEmit

cd src-tauri
cargo test --lib
cd ../..
```

任一步红 → 修完再来,不要带病推 tag(tag 误推后回滚很麻烦,见 §4)。

### 2.2 提交代码到 main

```bash
git status                # 确认改动符合预期
git add -A
git commit -m "feat: ..."  # 英文 commit message,遵循 conventional commits
git push origin main
```

⚠️ tag 必须基于 main 上**最新**的 commit。否则推出去的 tag 指向旧 commit,Release 里跑的是老代码。

### 2.3 创建 annotated tag(关键步骤)

```bash
# annotated tag 与 lightweight tag 的本质区别:
#   - lightweight (git tag v0.3.0):只是一个指针,不携带任何元数据
#   - annotated (git tag -a v0.3.0 -m "..."):是一个完整对象,包含 tagger、时间、message
#
# release.yml 里 tauri-action 需要 annotated tag 才能正确生成 Release 信息
# 而且 GitHub 在 Release 页面会展示 tag 的 message 作为辅助上下文。

git tag -a v0.3.0 -m "Release v0.3.0

- 新功能 1 的一句话描述
- 新功能 2 的一句话描述
- Bug 修复 1"
```

**版本号规范**(SemVer 三段式):

| 改动类型 | 影响 | 版本号变化 |
|---|---|---|
| 不兼容的破坏性变更 | MAJOR+1, MINOR=0, PATCH=0 | `0.x.y` → `1.0.0` |
| 新增向下兼容的功能 | MINOR+1, PATCH=0 | `0.2.5` → `0.3.0` |
| 向下兼容的 Bug 修复 | PATCH+1 | `0.3.0` → `0.3.1` |

⚠️ **tag 必须以 `v` 前缀开头**(`v0.3.0` 而非 `0.3.0`):
- `release.yml` 的触发条件是 `tags: ['v*']`,不带 v 的 tag 不会触发
- `sync-version.js` 会自动 strip `v` 前缀,所以 manifest 里写的是 `0.3.0`

### 2.4 推送 tag,触发 workflow

```bash
git push origin v0.3.0
```

推送成功后**立即**打开浏览器:

> https://github.com/shetengteng/DiskMind/actions

应该能看到一条新的 `Release` workflow run,三个 job 并行:
- `build (macos-aarch64)`
- `build (macos-x86_64)`
- `build (windows-x64)`

总耗时约 **8-15 分钟**(首次冷缓存可能 20 分钟+,有 Rust cache 后会大幅加速)。

### 2.5 验收阶段:确认产物

跑完后打开:

> https://github.com/shetengteng/DiskMind/releases

应该看到一条 **草稿** `DiskMind v0.3.0`,展开 Assets,确认有以下文件且**版本号正确**:

| 文件名模板 | 平台 | 备注 |
|---|---|---|
| `DiskMind_0.3.0_aarch64.dmg` | macOS Apple Silicon | 主分发包 |
| `DiskMind_0.3.0_aarch64.app.tar.gz` | macOS Apple Silicon | 给 updater 用,目前未启用 |
| `DiskMind_0.3.0_x64.dmg` | macOS Intel | 主分发包 |
| `DiskMind_0.3.0_x64.app.tar.gz` | macOS Intel | 同上 |
| `DiskMind_0.3.0_x64-setup.exe` | Windows | NSIS 安装器 |
| `DiskMind_0.3.0_x64_en-US.msi` | Windows | MSI 安装器(企业部署) |

⚠️ **如果文件名是 `DiskMind_0.1.0_*`** → `sync-version` 步骤没生效,排查方向见 §3。

### 2.6 Publish:把草稿转正

确认无误后,在 Release 草稿页面顶部:
1. 可选:在 release body 上方编辑区写 changelog(默认 body 已包含安装注意事项 + 链接到开发待办)
2. 检查 `Set as the latest release` 勾上
3. 点击 **`Publish release`** 按钮

发布后用户可以从 https://github.com/shetengteng/DiskMind/releases/latest 下载,DiskMind 应用内的「检查更新」按钮(`Settings → 应用 → 检查更新`)也会通过 `/repos/shetengteng/DiskMind/releases/latest` API 命中这条 release。

## 3. 常见排查清单

### 3.1 workflow 没触发

- ✅ Tag 必须以 `v` 开头(`v0.3.0`,不能是 `0.3.0`)
- ✅ 必须是 push 到远程,本地 tag 不算
- ✅ 当前 default branch 上的 `release.yml` 必须存在(workflow 文件本身的版本以 default branch 为准)

### 3.2 `Sync version` 步骤报错

```
❌ 无效的版本号格式: main
```
→ 这是手动触发(`workflow_dispatch`)时跑了 sync,逻辑 bug。当前版本 `release.yml` 已修复(`if: github.event_name == 'push'`),如果还见到这个错说明你在用旧版 yml。

```
❌ 无法找到 Cargo.toml 中的 version 字段
```
→ `Cargo.toml` 的 `version = "..."` 行被改坏了。`sync-version.js` 用正则 `^version = ".*?"$/m` 匹配,如果你把 version 写成多行或加了注释,会失配。回退 Cargo.toml 后再试。

### 3.3 产物文件名还是旧版本号

- 确认 `Sync version` 步骤是绿的(没被 skip,没失败)
- 进 run summary 看这一步 stdout 是否打印了 `✅ 更新 tauri.conf.json: 0.3.0` 和 `✅ 更新 Cargo.toml: 0.3.0`
- 如果显示 `⏭️ 已是最新版本`,说明 manifest 已经手工预先改过,这是正常路径,产物名应该是新版本号

### 3.4 macOS 用户反馈"打不开" / "已损坏"

预期行为 — Round 11 决定不做 Apple Developer ID 签名 + Notarization。在 release notes 里已经写了解决方法:

```bash
xattr -dr com.apple.quarantine /Applications/DiskMind.app
```

或者右键 `.app` → "打开" → 弹窗里再点"打开"。

### 3.5 Windows SmartScreen 警告"未知发布者"

预期行为 — Round 11 决定不做 EV Code Signing。指引用户:
- 点"更多信息" → "仍要运行"

### 3.6 Build 步骤 timeout / Rust 编译报错

- 大概率是某个依赖 crate 升级导致的(macOS / Windows SDK 兼容性)
- 在 Actions UI 上点开失败 job,从 `Compiling xxx v0.x.x` 这一行往下读错误堆栈
- 本地用对应平台 reproducible:`cd app && pnpm tauri:build`

## 4. tag 推错了怎么回滚

**已 push 但还未 Publish Release**:

```bash
# 删本地 tag
git tag -d v0.3.0

# 删远程 tag(等价于撤销触发)
git push origin :refs/tags/v0.3.0
# 或更直观的语法
git push --delete origin v0.3.0

# 进 Releases 页面把草稿 Discard 掉
```

⚠️ **已 Publish Release 后**:
- 不建议直接删除 Release(已经下载的用户的"检查更新"会失效)
- 优先策略:再发一个 patch 版本(`v0.3.1`)修问题,在 `v0.3.0` 的 release body 顶部加红字"⚠️ 此版本存在 X 问题,请升级 v0.3.1"
- 万不得已要删:Releases 页面 → 草稿/已发布的 Release → Delete release;然后再删 tag

## 5. 关键文件依赖关系图

```
.github/workflows/release.yml
    ├── 步骤"Sync version" → 调用 ↓
    │       app/package.json:scripts.sync-version → node ../scripts/sync-version.js
    │           ├── 写 app/src-tauri/tauri.conf.json (version 字段)
    │           └── 写 app/src-tauri/Cargo.toml      (version = "...")
    │
    ├── 步骤"Build & publish" → tauri-apps/tauri-action@v0
    │       └── 读 上面两个 manifest 决定产物文件名
    │
    └── 触发条件 ← git push origin v* (annotated tag,前缀 v,符合 SemVer)
```
